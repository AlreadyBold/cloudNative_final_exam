# 개발 과정과 고민

내약통한눈에를 만들면서 부딪힌 문제, 고민한 점, 그리고 어떻게 결정했는지를 정리한 문서입니다.
각 항목은 **문제 → 고민 → 결정과 결과** 순서로 적었습니다.

## 1. 과제 요건을 어떻게 맞췄나

### 컨테이너 7개
- **요건** : 역방향 프록시, DB, 프론트, 서버 2대 이상, 세션 공유 서버를 포함해 컨테이너 6개 이상.
- **고민** : 서버를 종류별로 1대씩만 두면 "세션이 서버 사이에서 공유된다"는 것을 화면으로 보여 주기 어렵습니다.
  같은 회원 서버가 2대 있어야 요청이 번갈아 가도 로그인이 유지되는 것을 확인할 수 있습니다.
- **결정** : 회원 서버(user-api)를 2대로 늘려 7개로 구성했습니다.
  프록시가 두 서버에 번갈아 요청을 보내고, 관리자 화면의 "세션 공유 확인"에서 어느 서버가 응답했는지와 세션 ID가 같은지를 보여 줍니다.

| 컨테이너 | 역할 |
|---|---|
| alyak-proxy | 역방향 프록시 (경로별 분배, user-api 2대 번갈아 분배) |
| alyak-front | 화면 (순수 HTML/CSS/JS) |
| alyak-user-api-1, -2 | 회원·로그인·처방내역 불러오기·관리자 (Spring Boot) |
| alyak-pill-api | 약 검색·내 약통·함께 먹는 약 검사 (FastAPI) |
| alyak-redis | 세션 공유 저장소 |
| alyak-mysql | DB |

### 이기종 서버 (가산점)
- **고민** : 언어가 다른 서버끼리 로그인 세션을 어떻게 같이 쓸 것인가.
  Spring Session의 기본 저장 방식은 Java 직렬화라서 Python에서 읽을 수 없습니다.
- **결정** : Spring Session이 세션을 **JSON으로** Redis에 저장하도록 바꿨습니다.
  FastAPI(pill-api)는 브라우저가 보낸 `SESSION` 쿠키 값으로 Redis에서 `alyak:session:sessions:<세션ID>`를 직접 읽어
  로그인한 사용자를 확인합니다. 세션을 쓸 때 만료 시간도 Spring과 같은 규칙으로 늘려 줍니다.
- **결과** : 로그인은 Spring 서버에서 하고, 약통 요청은 Python 서버가 받아도 같은 사용자로 처리됩니다.
  프록시 한 곳(같은 주소)으로만 접속하므로 쿠키가 세 서버 모두에 똑같이 전달됩니다.

### Docker Compose 금지
- **결정** : 모든 과정을 Docker CLI 명령으로만 구성했습니다.
  `scripts/00_env.sh`(비밀값 파일) → `01_network.sh`(네트워크) → `02_build.sh`(이미지) → `03_run.sh`(컨테이너) 순서로 실행합니다.
- 실행한 `docker build`, `docker run` 명령은 [COMMANDS.md](COMMANDS.md)에 순서대로 적었고, 스크립트 내용과 한 글자씩 같은지 확인했습니다.

### 네트워크와 데이터 보존
- **사용자 정의 브리지 네트워크(`alyak-net`)** : 기본 bridge 네트워크와 달리 컨테이너 이름으로 서로를 찾을 수 있습니다(도커 내장 DNS).
  그래서 설정에 IP 대신 `alyak-mysql`, `alyak-redis` 같은 이름을 씁니다.
- **외부 포트 최소화** : 밖으로 연 포트는 프록시(8080)와 확인용 DB(33307)뿐입니다. 서버들은 네트워크 안에서만 통신합니다.
- **바인드 마운트** : DB 데이터를 호스트의 `~/alyak/mysql-data`에 저장해서, MySQL 컨테이너를 지우고 다시 만들어도 회원·약통 데이터가 남습니다.

### 순수 HTML/JS 프론트와 주석
- 빌드 도구(npm, 번들러) 없이 ES 모듈과 Fetch API만으로 만들었습니다. nginx가 파일을 그대로 내려 줍니다.
- 모든 코드(Java, Python, JS, SQL, nginx 설정, 스크립트)에 "무엇을 왜 하는지" 주석을 달았습니다.

## 2. 보안과 개인정보

### 비밀번호가 코드에 들어 있던 문제
- **문제** : 개발 초기에 MySQL root 비밀번호와 DB 계정 비밀번호를 설정 파일과 스크립트에 직접 적어 두었습니다.
  공개 저장소라 누구나 볼 수 있는 상태였습니다.
- **결정**
  - 비밀값을 모두 env 파일(`env/mysql.env`, `env/user-api.env`, `env/pill-api.env`)로 옮기고 git에서 제외했습니다.
  - `scripts/00_env.sh`가 실행할 때마다 **무작위 비밀번호**로 env 파일을 만들어 줍니다.
  - DB 계정은 이미지에 비밀번호를 넣지 않고, 컨테이너가 처음 뜰 때 env 값으로 만듭니다(`db/initdb/02_create_accounts.sh`).
  - 이미 올라간 이력에서도 비밀번호가 보이지 않도록 git 이력을 다시 작성했습니다.
- **교훈** : 비밀값은 처음부터 env로 관리해야 합니다. 나중에 지우면 이력까지 정리해야 해서 일이 커집니다.

### 주민등록번호와 개인정보
- 처방내역 조회(간편인증)에는 이름·주민등록번호·휴대폰 번호가 필요합니다.
- **결정**
  - 주민등록번호는 서버에 **저장하지 않고** 인증 요청에만 씁니다.
  - 입력칸을 앞자리·뒷자리로 나누고 뒷자리는 가려서 입력받습니다. 브라우저 자동완성도 껐습니다.
  - 인증 요청 후에는 입력칸을 비우고 가린 요약만 보여 줍니다.
  - 휴대폰 번호는 하이픈을 자동으로 넣고, 서버 로그에는 간편인증 ID를 가려서 남깁니다.
  - 관리자 화면의 세션 표에서도 이메일을 가립니다.

### 관리자 권한의 범위
- **고민** : 관리자가 모든 것을 볼 수 있으면 편하지만, 사용자가 먹는 약은 민감한 건강 정보입니다.
- **결정** : 관리자는 회원 목록, 비밀번호 초기화, 컨테이너 상태, 세션 확인만 할 수 있고 **사용자의 약통·처방 정보는 볼 수 없습니다.**
  비밀번호를 초기화하면 그 회원은 바로 로그아웃되고, 다음 접속 때 이유를 안내받습니다.

## 3. 세션과 로그인

### 계정당 로그인 1개
- **고민** : 같은 계정으로 여러 기기에서 동시에 처방내역을 불러오면 간편인증이 꼬일 수 있습니다.
  "먼저 로그인한 쪽을 지킬지, 나중 로그인을 허용할지"를 정해야 했습니다.
- **결정** : **나중 로그인 우선**입니다. 새 기기에서 로그인하면 이전 기기의 세션을 끝냅니다.
  Redis에 `alyak:login:user:<사용자ID>` = 현재 세션 ID를 기록하고, 끊긴 세션에는 `alyak:login:ended:<세션ID>`에 이유(다른 기기 로그인 / 비밀번호 초기화)를 남깁니다.

### 이전 기기에 바로 알리기
- **문제** : 세션을 지워도 이전 기기는 다음 요청을 보내기 전까지 끊긴 줄 모릅니다.
- **결정** : 화면이 5초마다, 그리고 탭으로 돌아올 때 세션 상태를 확인하고, 끊겼으면 이유와 함께 로그인 화면으로 보냅니다.

### 상태를 확인하는 요청이 세션을 연장해 버린 문제
- **문제** : 5초마다 상태를 묻는 요청 때문에, 사용자가 아무것도 하지 않아도 세션이 만료되지 않았습니다.
  Spring MVC가 요청을 처리하는 과정에서 세션을 열기 때문에 세션의 마지막 사용 시각이 갱신됐습니다.
- **결정** : 상태 확인(`GET /api/user/session/status`)을 Spring Session보다 **앞단의 서블릿 필터**(`SessionStatusFilter`)에서 처리하도록 옮겼습니다.
  이 필터는 Redis를 읽기만 하고 세션을 열지 않습니다.
- **결과** : 상태 확인은 세션 만료 시간에 영향을 주지 않고, 실제로 화면을 쓸 때만 세션이 연장됩니다.

## 4. 인프라에서 생긴 문제

### 컨테이너를 다시 만들면 프록시가 옛 IP로 요청하던 문제
- **문제** : 서버 컨테이너를 지우고 다시 만들면 IP가 바뀌는데, nginx는 시작할 때 한 번 찾은 IP를 계속 써서 502 오류가 났습니다.
- **결정** : 프록시 설정에 도커 내장 DNS(`resolver 127.0.0.11 valid=10s`)를 지정하고,
  upstream에 공유 메모리(`zone`)와 `server ... resolve`를 넣어 10초마다 IP를 다시 확인하도록 했습니다(nginx 1.27.3 이상 기능).
- **결과** : 서버 하나만 다시 만들어도 프록시를 재시작할 필요가 없습니다.

### CSS가 `hidden` 속성을 덮어쓴 문제
- **문제** : JS에서 요소에 `hidden`을 달았는데도 화면에 그대로 보였습니다. CSS의 `display: flex` 같은 설정이 `hidden`보다 우선했기 때문입니다.
- **결정** : `[hidden] { display: none !important; }`를 넣어 `hidden`이 항상 이기게 했습니다.

### 디스크 용량
- **문제** : 개발 VM의 디스크가 작아서, 공공데이터 원본(약 1.3GB)과 여러 이미지 빌드로 공간이 부족해졌습니다.
- **결정**
  - 원본 데이터는 이미지에 넣지 않고, 필요한 열만 뽑아 압축한 SQL 초기화 파일(`03_insert_pill_catalog.sql.gz`, 약 5MB)만 이미지에 넣었습니다.
  - 원본은 압축해서 보관하고(약 55MB), 빌드 후에는 쓰지 않는 이미지와 빌드 캐시를 정리합니다.
  - 회원 서버(Spring Boot) 이미지는 빌드 단계와 실행 단계를 나눠(멀티 스테이지), 실행 이미지에는 JRE와 jar만 담았습니다.
  - 약 서버(FastAPI) 이미지는 slim 기반 이미지를 써서 크기를 줄였습니다.

## 5. 약 데이터

### 카탈로그 만들기
- **고민** : 약 정보가 여러 기관에 흩어져 있고 형식도 다릅니다.
- **결정** : 공공데이터 세 종류를 합쳐 하나의 카탈로그로 만들었습니다.
  - 식품의약품안전처 : 의약품 허가 정보(이름, 성분, 원료 성분, ATC 약효 분류, 성상)
  - 건강보험심사평가원 DUR : 병용금기, 임부금기, 연령금기, 노인주의 등
  - 약가마스터 : 보험코드(EDI)와 표준코드 대응표
- 변환 도구(`tools/build_catalog_sql.py`)가 원본을 읽어 DB 초기화 SQL을 만들고, MySQL 컨테이너가 처음 뜰 때 자동으로 넣습니다.
  그래서 설치하는 사람은 원본 데이터 없이도 바로 약 46,292건을 검색할 수 있습니다.

### 처방 약을 카탈로그에 연결하기
- **문제** : 처방내역에는 약 이름과 보험코드가 오는데, 이름 표기가 조금씩 다르고 보험코드는 바뀐 경우가 있습니다.
  잘못 연결하면 다른 약의 주의 정보를 보여 주게 되어 위험합니다.
- **결정** : 정확한 것부터 차례로 맞춥니다.
  1. 보험코드(EDI)로 찾습니다. 여러 개면 정상 판매 중인 약을 먼저 고릅니다.
  2. 약가마스터로 바뀐 보험코드도 옛 코드와 연결합니다.
  3. 코드로 못 찾으면 이름을 정리(공백·괄호 등 제거)해서 찾되, **딱 하나만 나올 때만** 연결합니다. 여러 개면 연결하지 않습니다.
- **결과** : 표본 기준 약 96.6%를 연결했습니다. 연결되지 않은 약도 약통에는 담기고, "검사 정보 없음"으로 표시됩니다.

### 병용금기 검사 범위 넓히기
- **문제** : 처음에는 병용금기 검사가 가능한 약이 7,277개뿐이었습니다. DUR 자료는 "성분" 기준인데, 약마다 어떤 성분이 들었는지 연결된 데이터가 부족했기 때문입니다.
- **결정** : 약별 성분코드 자료를 추가로 넣어 약 → 성분 → 병용금기를 이어 주었습니다.
- **결과** : 검사 가능한 약이 **30,932개**로 늘었습니다.

### 같은 성분, 같은 효능 검사
- **고민** : 병용금기가 아니어도 위험한 경우가 있습니다. 예를 들어 감기약과 진통제에 같은 성분이 들어 있으면 과다 복용이 됩니다.
- **결정** : 복용 기간이 겹치는 약끼리 세 가지를 검사합니다.
  - ⚠ **병용금기** (DUR) : 사유와 함께 먹게 되는 기간을 보여 줍니다.
  - ⚠ **같은 성분 중복** : 원료 성분 기준이라 복합제 안의 성분도 잡아냅니다.
  - ℹ **같은 효능** : ATC 약효 분류가 같은 약입니다. 의도된 처방일 수 있어 경고가 아닌 안내로 보여 줍니다.

## 6. 처방내역 불러오기 (CODEF)

### 같은 계정의 동시 인증 막기
- **문제** : 간편인증은 "요청 → 휴대폰에서 승인 → 확인" 두 단계라서, 같은 계정에서 동시에 두 번 진행하면 서로 꼬입니다.
  서버가 2대라 서버 메모리로는 막을 수 없습니다.
- **결정** : Redis에 계정별 잠금(`SET NX`, 270초)을 걸고, 잠금을 건 요청만 풀 수 있게 Lua 스크립트로 확인 후 해제합니다.
  두 서버가 같은 Redis를 보므로 어느 서버로 요청이 가도 똑같이 막힙니다.

### 하루 5번 제한
- **고민** : 외부 유료 API라서 무제한으로 부를 수 없습니다. 언제 횟수를 셀지(버튼을 누를 때, 성공했을 때, 실제로 호출할 때)를 정해야 했습니다.
- **결정** : **계정당 하루 5번**, CODEF를 실제로 호출하는 시점에 1을 더합니다.
  "5 미만이면 1 증가"를 Lua 스크립트로 한 번에 처리해서, 두 서버에 동시에 요청이 와도 5번을 넘지 않습니다.
  키(`alyak:codef:daily:<사용자ID>:<날짜>`)는 하루가 지나면 저절로 사라지고, 횟수는 env로 바꿀 수 있습니다.

### 복용 기간 자동 계산
- **문제** : 처음에는 불러온 처방의 약마다 사용자가 복용 기간을 직접 고르게 만들었습니다.
  하지만 처방에는 이미 약마다 투약일수가 있어서, 사용자에게 다시 입력하게 하는 것은 불필요했습니다.
- **결정** : 약마다 **조제일 ~ 조제일 + 투약일수 − 1**로 서버가 자동 계산합니다. 화면에서는 계산된 기간과 상태만 보여 줍니다.
- **결과** : 처방 하나에 3일치 약과 30일치 약이 섞여 있어도 각각 맞는 기간으로 담깁니다.

### 샘플(MOCK) 모드
- **고민** : CODEF 키가 없는 사람(채점자 포함)도 기능을 확인할 수 있어야 합니다.
- **결정** : 키가 없으면 샘플 처방을 돌려줍니다.
- **문제와 수정** : 처음에는 샘플의 조제일이 고정 날짜라, 시간이 지나면 모든 약이 "복용 완료"로 보였습니다.
  조제일을 **"오늘 − 5일"**로 바꾸고 투약일수를 3·5·7·10·30일로 섞어서, 언제 실행해도 복용 완료·복용 중이 함께 보이고 병용금기 경고도 나타나게 했습니다.

## 7. 화면 정리

- **저장한 처방 화면 통합** : 처음에는 "저장한 처방"과 "내 약통"이 따로 있었는데, 같은 약이 두 곳에 있어 헷갈렸습니다. 처방은 불러오면 바로 내 약통에 담기도록 합쳤습니다.
- **복용법 표시** : 약마다 약효, 하루 복용 횟수, 1회 복용량, 투약일수를 한 줄로 보여 줍니다(예: "해열·진통·소염제 · 하루 3번 · 1번에 1개씩 · 7일분").
- **탭 고정** : 화면을 내려도 탭 메뉴가 상단에 남아 있어 다른 화면으로 바로 이동할 수 있습니다.
- **구역 나누기** : 내 약통을 "복용 캘린더"와 "약 목록" 카드로 나눠 한눈에 구분되게 했습니다.

## 8. 남은 한계

- 카탈로그에 연결되지 않은 약(이름이 여러 약과 겹치거나 카탈로그에 없는 약)은 함께 먹는 약 검사에서 빠집니다.
  잘못된 경고를 주는 것보다 "검사 정보 없음"으로 알리는 쪽을 택했습니다.
- 약 데이터는 DB를 처음 만들 때 넣은 시점의 공공데이터 기준입니다. 새 허가 약이나 바뀐 DUR 정보를 반영하려면 카탈로그를 다시 만들어야 합니다.
